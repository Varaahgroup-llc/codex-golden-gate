## Authority and maintenance

Jira records delivery status, dependencies and approval evidence. GitHub contains source, implementation PRs and public issue counterparts. Keep both sides linked during authorized work; this is not an unattended synchronization service. Open GitHub issues may correspond to To Do or In Progress in Jira. Do not mark a planned feature as completed because the tracking issue exists.

Reference GG issue keys in related branches, commits and PRs. Keep releases, changelogs, publisher records and review evidence scoped to Golden Gate. Do not place this product's work in another product's repository, Jira project or release ledger.

## Release gates

The initial v0.1.0 prerelease remains a draft. The raw-credential-entry prototype is not a directory-ready submission under the current restricted-data rule. GG-2 must resolve the policy/architecture decision; GG-3 must establish verified publisher/local-MCP eligibility; native Codex rendering and security/provider evidence must be completed before GG-7 can claim submission/readiness. No directory approval or listing currently exists.

Keep passwords, keys, tokens, private organization IDs, reviewer credentials and verification documents out of public source and GitHub issues. Use the private reporting/verification channels where appropriate.


GG-9 tracks the internal 0.3.0-rc.1 release rehearsal. The project Fix Version is a planning association. The bundle records completed slices of GG-4 through GG-9 without closing the broader acceptance items. Consult the [release register](releases/RELEASE_REGISTER.md) for distribution evidence.
